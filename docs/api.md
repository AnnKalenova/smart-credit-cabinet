# Описание API

REST API, JSON, версия `v1`. Спецификация OpenAPI 3.1 генерируется из кода.

| Что | Где |
|---|---|
| Swagger UI | http://localhost:8080/api/docs (через nginx) или http://localhost:8000/api/docs (напрямую) |
| ReDoc | http://localhost:8080/api/redoc |
| OpenAPI JSON | http://localhost:8080/api/openapi.json, копия в репозитории — [openapi.json](openapi.json) |
| Симулятор внешних систем | http://localhost:8001/docs, копия — [openapi-integrations-mock.json](openapi-integrations-mock.json) |
| Коллекция запросов Postman | [postman/smart-credit-cabinet.postman_collection.json](postman/smart-credit-cabinet.postman_collection.json) |

## Аутентификация

```http
POST /api/v1/auth/login
{"login": "smirnov", "password": "demo1234"}
→ {"access_token": "eyJ…", "token_type": "bearer", "user": {...}}
```

Дальше токен передаётся в заголовке `Authorization: Bearer <access_token>`. В Swagger — кнопка **Authorize**. Токен без срока действия, без пользователя или от другого издателя не принимается (401). Список демо-учёток — `GET /api/v1/auth/demo-accounts` (только в демо-режиме).

| Роль | Доступ |
|---|---|
| `CLIENT` | `/api/v1/applications/*`, `/companies/*`, `/products/*`, `/loans/*`, `/notifications/*` — только по своим компаниям |
| `ANALYST` | `/api/v1/bank/*`, кроме изменения параметров |
| `RISK_MANAGER` | `/api/v1/bank/*`, включая `PUT /bank/settings/{key}` |

## Ошибки

| Код | Когда | Тело |
|---|---|---|
| 400 | запрос не удалось прочитать (например, multipart без границы частей) | `{"detail": "Не удалось прочитать запрос — проверьте формат данных"}` |
| 401 | нет токена или он недействителен; неверный логин или пароль | `{"detail": "Требуется вход в систему"}` |
| 403 | не та роль или нет права подписи | `{"detail": "Выбрать условия кредита может руководитель или представитель по доверенности…"}` |
| 404 | объект не найден или принадлежит другой компании; демо-функция при `DEMO_MODE=false` | `{"detail": "Заявка не найдена"}`, `{"detail": "Недоступно"}` |
| 409 | действие недоступно в текущем статусе, конфликт версий, истёк срок предложения | `{"detail": "Действие недоступно: заявка в статусе «Готово предложение». Обновите страницу"}` |
| 413 | файл больше `MAX_UPLOAD_MB` | `{"detail": "Файл больше 10 МБ"}` |
| 422 | ошибка валидации или бизнес-проверки, в том числе символ NUL (`\u0000`) в тексте | `{"detail": {"message": "Проверьте введённые данные", "problems": ["Сумма: должно быть не больше 10 000 000 000"]}}` |
| 429 | слишком много попыток входа или кодов подписи (см. ниже) | `{"detail": "Слишком много неудачных попыток входа. Попробуйте через 10 минут"}` |
| 500 | непредвиденная ошибка | `{"detail": "Внутренняя ошибка сервиса. Попробуйте ещё раз", "request_id": "…"}` |

Ответы с ошибками валидации и бизнес-проверки содержат список `problems` на русском с названием поля — интерфейс показывает его пользователю как есть: «Заявка: некорректный идентификатор», «Сообщение: не может быть пустым», «Сумма: должно быть не меньше 1». Стандартные ответы фреймворка тоже по-русски: «Не найдено», «Метод не поддерживается», «Недостаточно прав». Символ NUL PostgreSQL не хранит, поэтому такой ввод получает 422 («недопустимый символ в тексте», в параметрах запроса — «недопустимые символы в данных»), а не 500.

Каждый ответ несёт заголовок `X-Request-ID`: по нему запрос находится в JSON-логах API. Присланный идентификатор принимается, только если он похож на идентификатор (латиница, цифры, `.`, `_`, `-`, до 64 символов), иначе API выдаёт свой.

Ограничения частоты (ответ 429):

| Что | Ограничение | Ответ |
|---|---|---|
| Неверный пароль к одному логину с одного адреса | 10 за 10 минут; с другого адреса пользователь входит как обычно, успешный вход обнуляет счётчик | «Слишком много неудачных попыток входа. Попробуйте через 10 минут» |
| Неверный пароль к одному логину со всех адресов | 50 за 10 минут | то же |
| Неудачные входы с одного адреса по любым логинам | 100 за 10 минут | «Слишком много неудачных попыток входа с вашего адреса. Попробуйте через 10 минут» |
| Запросы входа через nginx | 20 в минуту с адреса, пачкой до 10 | «Слишком много попыток входа. Попробуйте через минуту» |
| Коды подписи | 10 кодов за 10 минут по одной заявке; 5 вводов одного кода | «Слишком много запросов кода — попробуйте через 10 минут», «Слишком много попыток, запросите новый код» |

#### Конструктор условий

```json
POST /api/v1/applications/{id}/simulation
{"product_code": "EXPRESS", "amount": 1000000, "term_months": 12, "has_collateral": false, "owner_guarantee": false, "with_suggestions": true}
```

Все поля необязательные: не переданное берётся из заявки, поэтому пустой запрос `{}` возвращает решение на условиях заявки, подсказки и границы для элементов управления. Ответ для `kuznetsova` (экспресс-кредит 1 000 000 ₽ на 12 мес., встречное предложение):

```json
{
  "base": {"product_code": "EXPRESS", "amount": 1000000.0, "term_months": 12, "has_collateral": false, "owner_guarantee": false},
  "result": {
    "outcome": "COUNTER_OFFER",
    "verdict": "Предложим другие условия",
    "explanation": "На 12 мес. можно до 710 000 ₽: платежи по всем кредитам не должны превышать 40% поступлений на счёт",
    "automatic": true,
    "fixable": true,
    "rate": 21.5,
    "monthly_payment": 93353.91,
    "max_amount": 710000,
    "payment_share": 0.4208,
    "payment_share_cap": 0.4,
    "offers": [{"label": "Вся сумма на 18 мес.", "amount": 1000000.0, "term_months": 18, "rate": 21.5, "…": "…"}],
    "offer": null,
    "todo": []
  },
  "suggestions": [
    {
      "code": "term",
      "title": "Срок 24 мес.",
      "effect": "Одобрим автоматически вместо «предложим другие условия»",
      "params": {"product_code": "EXPRESS", "amount": 1000000.0, "term_months": 24, "has_collateral": false, "owner_guarantee": false},
      "result": {"outcome": "APPROVE", "verdict": "Одобрим автоматически", "rate": 21.5, "monthly_payment": 51631.57, "…": "…"}
    },
    {"code": "guarantee", "title": "Поручительство собственника", "effect": "Ставка 21% вместо 21,5%", "…": "…"}
  ],
  "products": [{"code": "EXPRESS", "name": "Экспресс-кредит", "min_amount": 300000.0, "max_amount": 5000000.0, "terms": [3, 6, 9, 12, 18, 24, 30, 36], "collateral": "NONE", "auto_decision_limit": 5000000.0, "…": "…"}]
}
```

С условиями варианта банка (`{"term_months": 18}`) в `result.offer` приходит этот вариант: `{"id": "…", "label": "Вся сумма на 18 мес.", "rate": 21.5, "monthly_payment": 65486.54}`.

- `outcome` — `APPROVE`, `COUNTER_OFFER`, `MANUAL_REVIEW`, `NEEDS_INFO` или `DECLINE`; `fixable: false` — отказ по стоп-фактору, другие условия его не исправят.
- `offer` — действующий вариант из предложения банка ровно на этих условиях (тот же продукт, сумма и срок, залог и поручительство как в заявке), только для заявки в OFFER_READY: `{id, label, rate, monthly_payment}`. Такой вариант выбирают через `offers/{id}/accept` — новая заявка не нужна. Иначе `null`.
- `todo` — что останется сделать в новой заявке на этих условиях, кроме согласий: «описать имущество для залога», «приложить документ: …» или «приложить документы: …».
- `suggestions` — до четырёх подсказок «что улучшит условия» (коды `guarantee`, `collateral`, `term`, `amount`, `product:<код>`), каждая с готовыми `params` и посчитанным `result`. Варианты из предложения банка в подсказках не повторяются. Другой продукт подсказывается, только если для него ничего не нужно дозаполнять (пустой `todo`). С `"with_suggestions": false` подсказки не считаются — так интерфейс пересчитывает решение, пока клиент двигает ползунок.
- Доступен клиенту по своей заявке после оценки: статусы MANUAL_REVIEW, OFFER_READY, SIGNING, DECLINED, CLIENT_DECLINED, EXPIRED, CANCELLED, если сведения ЕГРЮЛ, ФНС и БКИ получены. Иначе — 409 «Конструктор условий доступен после того, как банк оценит заявку». Если по заявке отказал кредитный специалист — 409 «По заявке решение принял кредитный специалист — условия подбирает он». Сотрудникам банка — 403, по чужой заявке — 404.
- Условия вне продукта — 422: «Сумма по продукту «Экспресс-кредит» — от 300 000 до 5 000 000 ₽», «Срок по продукту «Экспресс-кредит» — 3–36 мес.», «Продукт «Инвестиционный кредит» не подходит для цели заявки».

Логика расчёта и подсказок — [decision-logic.md](decision-logic.md#конструктор-условий).

#### Новая заявка на основе этой

```json
POST /api/v1/applications/{id}/reapply
{"term_months": 24, "replace_current": true}
→ 201, новый черновик: {"status": "DRAFT", "parent_id": "<id исходной>", "term_months": 24, …}
```

- Тело необязательное, поля — как у конструктора (`product_code`, `amount`, `term_months`, `has_collateral`, `owner_guarantee`) плюс `replace_current` (по умолчанию `false`); не переданное берётся из исходной заявки. Без тела — повторная подача на тех же условиях.
- Для закрытых заявок (DECLINED, EXPIRED, CLIENT_DECLINED, CANCELLED) создаётся новый черновик.
- С `"replace_current": true` можно заменить открытую заявку новой одним действием. Заявку с предложением (OFFER_READY) заменяет только подписант: отказ от предложения, событие «Отказ от предложения: клиент подаёт заявку на других условиях»; если предложение уже истекло, исходная заявка переходит в EXPIRED, а новый черновик всё равно создаётся. Заявку на ручном рассмотрении (MANUAL_REVIEW) заменяет тот, кто может её отозвать, — подписант: отзыв, событие «Заявка отозвана: клиент подаёт её на других условиях». Закрытие исходной заявки и новый черновик — одна транзакция: при ошибке в условиях (422) исходная заявка не меняется. Без права на отказ или отзыв — 403.
- Без `replace_current` открытая заявка, как и раньше, даёт 409 «Действие недоступно: заявка в статусе «Готово предложение». Обновите страницу».
- Переносятся описание задачи, выручка, залог и его описание, поручительство и документы. Документы переносятся ссылкой на тот же файл, без копирования: файл удаляется из хранилища, только когда на него не ссылается ни одна заявка. Согласия не переносятся — их подписывают заново.
- По одной исходной заявке может быть одна незакрытая новая. Повторный вызов — 409 «По этой заявке уже создана новая — № 2026-000004. Откройте её в списке заявок»; в заявке её видно в `next_application`, а `permissions.can_reapply` — `false`.
- Продукт не под цель исходной заявки — 422 «Продукт не подходит для цели заявки». Сумма и срок из тела — в пределах продукта, иначе 422 с границами, как у конструктора: «Сумма по продукту «Экспресс-кредит» — от 300 000 до 5 000 000 ₽».

#### Передать условия руководителю

```json
POST /api/v1/applications/{id}/request-signature
{"conditions": {"amount": 400000, "term_months": 12, "owner_guarantee": true}}
```

- Для сотрудника без права подписи, когда заявка в OFFER_READY или MANUAL_REVIEW. Подписанту — 409 «У вас есть право подписи — подпишите сами».
- Условия проверяются так же, как в конструкторе: вне продукта — 422, конструктор недоступен — 409.
- Подписанты получают уведомление «Новые условия по заявке № …»: «Орлова Мария Петровна (главный бухгалтер) предлагает подать новую заявку: Экспресс-кредит, 400 000 ₽ на 12 мес., с поручительством собственника. Откройте заявку — условия уже в конструкторе.» В журнал пишется событие `CONDITIONS_PROPOSED` «Руководителю переданы условия для новой заявки: …».
- В заявке появляется `proposed_conditions`: `{"conditions": {…все поля условий…}, "text": "Экспресс-кредит, 400 000 ₽ на 12 мес., с поручительством собственника", "by": "Орлова Мария Петровна", "at": "…"}`. Поле видно, пока статус заявки не сменился. У подписанта конструктор открывается сразу с этими условиями, подать по ним заявку — `reapply` с `replace_current`.
- Без тела — прежнее поведение: «Нужна ваша подпись» для черновика, предложения или договора (DRAFT, OFFER_READY, SIGNING).

### Банк

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/bank/applications?scope=queue\|active\|mine\|all&status=&product=&q=` | очередь и реестр; банк видит только отправленные заявки. В очереди (`queue`) — ручное рассмотрение и выдачи, которые не прошли после всех попыток. В строке — `triggers` (причины ручного рассмотрения) и `awaiting_reply` (последнее сообщение — от клиента, он ждёт ответа) |
| GET | `/api/v1/bank/applications/{id}` | досье: сведения источников, скоринг с факторами, проверки, решения, предложения, журнал, вызовы систем, подсказки по ставкам, права (`can_decide`, `can_rerun`, `can_retry_disbursement`) |
| POST | `/api/v1/bank/applications/{id}/assign` | взять в работу — только заявку на ручном рассмотрении; заявку, которую уже рассматривает другой специалист, передаёт риск-менеджер (иначе 409 «Заявку уже рассматривает … Передать её может риск-менеджер») |
| POST | `/api/v1/bank/applications/{id}/decision` | решение: `APPROVE` (варианты условий), `REQUEST_INFO` (что предоставить), `DECLINE` (причина) |
| POST | `/api/v1/bank/applications/{id}/rerun` | на ручном рассмотрении — повторить автоматическую проверку (после сбоя источника); при сбое выдачи — повторить выдачу |
| GET | `/api/v1/bank/applications/{id}/documents/{doc_id}` | скачать документ клиента |
| GET / POST | `/api/v1/bank/applications/{id}/messages` | переписка с клиентом |
| GET | `/api/v1/bank/dashboard` | воронка, статусы, доля автоматических решений, время до решения, SLA, выдачи, ждущие повтора, интеграции |
| GET | `/api/v1/bank/settings` | параметры политики |
| PUT | `/api/v1/bank/settings/{key}` | изменить ключевую ставку или подпись к ней (риск-менеджер) |
| GET / POST | `/api/v1/bank/integrations/faults` | состояние и моделирование сбоев внешних систем (только в демо-режиме) |

Пример решения аналитика:

```json
POST /api/v1/bank/applications/{id}/decision
{
  "action": "APPROVE",
  "offers": [{"product_code": "INVESTMENT", "amount": 25000000, "term_months": 60, "rate": 16.5}],
  "message_to_client": "Одобрили инвестиционный кредит, залог — приобретаемый станок.",
  "comment_internal": "Финансовое положение устойчивое"
}
```

Если `rate` не указана, ставка считается по политике. Отклонение от политики сохраняется в расшифровке ставки как «корректировка кредитного специалиста». Правила решения:

- решение принимается только на ручном рассмотрении; если заявку взял в работу другой специалист, решает он или риск-менеджер (иначе 409 «Заявку рассматривает …: решение принимает этот специалист или риск-менеджер»);
- одобрить можно только после проверки по ЕГРЮЛ, ФНС и БКИ: если источник был недоступен, сначала `rerun` (иначе 409);
- продукт — под цель заявки, сумма и срок — в пределах продукта, ставка — в коридоре продукта (иначе 422 с границами: «Ставка по продукту «Инвестиционный кредит» — от 15% до 24%»);
- если среди вариантов есть запрошенные условия — это одобрение, иначе — встречное предложение;
- для отказа нужна причина, для запроса — хотя бы один пункт.

Повтор выдачи. Если АБС не ответила за все 30 попыток, заявка остаётся в статусе DISBURSEMENT: договор подписан, отозвать его клиент не может. Она попадает в очередь специалиста с причиной «Выдача не прошла — повторите её, когда АБС снова доступна», в досье `can_retry_disbursement: true`. Специалист вызывает `rerun`, когда АБС снова доступна. Запрос в АБС идемпотентен (ключ — ID заявки), поэтому повтор не создаст второй кредит. Если выдача ещё идёт — 409 «Выдача ещё выполняется — повтор не нужен».

Параметры политики меняет только риск-менеджер, остальным — 403 «Менять параметры кредитной политики может только риск-менеджер». Ключевая ставка (`key_rate`) — число больше 0 и меньше 50, можно с запятой (`"15,5"`); при изменении подпись к ней (`key_rate_note`) сама становится «Установлена в банке ДД.ММ.ГГГГ». Подпись можно задать и отдельно — непустой текст до 300 символов. Неизвестный параметр — 404.

### Только в демо-режиме

При `DEMO_MODE=false` эти функции выключены и отвечают 404 «Недоступно»: список демо-учёток (`/auth/demo-accounts`), пример документа (`/documents/demo`), моделирование сбоев (`/bank/integrations/faults`). Код подписи в ответе `sign-challenges` не возвращается (`demo_code: null`) — в рабочей версии его доставляет канал банка, в этой сборке он не подключён. Демо-учётки с общеизвестным паролем не создаются, а оставшиеся в базе с демо-стенда отключаются при старте API.

## Основной сценарий через curl

```bash
BASE=http://localhost:8080
TOKEN=$(curl -s $BASE/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"login":"smirnov","password":"demo1234"}' | jq -r .access_token)
AUTH="Authorization: Bearer $TOKEN"
COMPANY=$(curl -s $BASE/api/v1/auth/me -H "$AUTH" | jq -r '.companies[0].id')

# черновик
APP=$(curl -s $BASE/api/v1/applications -H "$AUTH" -H 'Content-Type: application/json' \
  -d "{\"company_id\":\"$COMPANY\",\"product_code\":\"WORKING_CAPITAL\",\"purpose\":\"WORKING_CAPITAL\",\"amount\":3000000,\"term_months\":12}" | jq -r .id)

# согласия: код подписи (в демо-режиме возвращается в ответе)
CH=$(curl -s $BASE/api/v1/applications/$APP/sign-challenges -H "$AUTH" -H 'Content-Type: application/json' -d '{"purpose":"CONSENTS"}')
curl -s $BASE/api/v1/applications/$APP/consents -H "$AUTH" -H 'Content-Type: application/json' \
  -d "{\"challenge_id\":$(echo $CH | jq .challenge_id),\"code\":$(echo $CH | jq .demo_code)}" > /dev/null

# отправка и ожидание решения
curl -s -X POST $BASE/api/v1/applications/$APP/submit -H "$AUTH" > /dev/null
sleep 10
curl -s $BASE/api/v1/applications/$APP -H "$AUTH" | jq '{status, decision: .decision.outcome, offers: [.offers[] | {amount, term_months, rate, monthly_payment}]}'

# конструктор условий: решение при сроке 18 мес.
curl -s $BASE/api/v1/applications/$APP/simulation -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"term_months":18}' | jq '{verdict: .result.verdict, rate: .result.rate, payment: .result.monthly_payment, tips: [.suggestions[].title]}'
```

## Контракты внешних систем (симулятор)

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/egrul/v1/entities/{inn}` | статус, дата регистрации, руководитель (с датой назначения), учредители, ОКВЭД, адрес |
| GET | `/fns/v1/transparent-business/{inn}` | режим налогообложения, выручка, прибыль, налоговый долг, блокировки счетов, массовый адрес, недостоверность |
| POST | `/bki/v1/credit-reports` | `{"inn", "consent_id"}` → балл БКИ, длина истории, просрочки, запросы за 30 дней, кредиты с платежами |
| POST | `/abs/v1/loans` | `{"inn", "contract_number", "product_code", "amount", "term_months", "rate", "settlement_account", "idempotency_key"}` → номер ссудного счёта; повтор с тем же ключом возвращает тот же результат |
| GET / POST | `/_control/faults` | `{"service": "EGRUL" \| "FNS" \| "BKI" \| "ABS", "mode": "down" \| "slow" \| "ok", "duration_seconds": 120}` (от 10 до 3600 с) |

Симулятор добавляет задержку 150–600 мс к каждому ответу. В режиме `slow` ответ приходит через 8 секунд — дольше таймаута API (5 с), поэтому срабатывают повторы.
