# Целевые показатели и нагрузочный прогон

Кейс не задаёт SLA для прототипа, но предлагает командам самим определить критичные операции, целевые показатели и способы их обеспечения. Здесь — что мы считаем критичным для клиента и банка, какие цели ставим, чем это измеряется в работающей системе и что показал нагрузочный прогон.

## Критичные операции и цели

| Операция | Почему критична | Цель | Чем обеспечивается |
|---|---|---|---|
| Автоматическое решение: от отправки заявки до предложения, запроса, отказа или передачи специалисту | клиент ждёт на экране; решение «за секунды» — главное обещание кабинета | одиночная заявка — до 10 с без демо-паузы (с демо-паузой 1,2 с между этапами — до 20 с); при всплеске подач p95 — не больше 60 с, первое решение — не позже 10 с | воркеры масштабируются горизонтально (`--scale worker=N`); очередь ведёт заявки в порядке отправки; этап внешнего источника — таймаут 5 с, до 5 повторов |
| Ответ API на действия клиента: черновик, подпись, отправка, ответ на запрос | это то, что клиент делает руками | p95 — до 500 мс при обычной нагрузке; в пик одновременной подачи — до 3 с | обычные маршруты выполняются в пуле потоков, пул БД — по числу потоков; при исчерпании пула — быстрый 503 с `Retry-After`, а не 500 через полминуты |
| Опрос статуса заявки в обработке (кабинет — раз в 1,2 с) | идёт постоянно у всех ждущих клиентов | p95 — до 200 мс при обычной нагрузке, до 1 с в пик | лёгкий запрос (одна заявка с событиями); индексы по заявке |
| Очередь этапов конвейера | растущая очередь = растущее время до решения | не растёт дольше 5 минут подряд; на один воркер — не больше 50 ожидающих этапов | метрика `pipeline_queue_depth{status="PENDING"}`; сигнал — добавить воркеры |
| Выдача после подписания договора | договор подписан, отменить нельзя | до 10 с; если АБС недоступна — повтор до 30 раз с паузой до 30 с, затем очередь специалиста с кнопкой «Повторить выдачу» | идемпотентный запрос в АБС (ключ — ID заявки) |
| Ручное рассмотрение | заявка ждёт человека | решение за 4 часа (`MANUAL_REVIEW_SLA_HOURS`) | срок виден в очереди специалиста, просрочка подсвечена и попадает в мониторинг |
| Ошибки сервиса | клиент не должен терять заявку | ответов 5xx — меньше 0,1 %; при перегрузке — 503 с понятным текстом, кабинет предлагает повторить; данные черновика не теряются (автосохранение не отправляет заявку со старыми условиями) | см. [architecture.md](architecture.md), раздел «Надёжность» |

## Чем измеряется в работающей системе

- Метрики Prometheus на `/metrics` API: `http_request_duration_seconds` (гистограмма по маршруту и методу — p50/p95 ответов), `http_requests_total` (по статусам — доля 5xx), `pipeline_queue_depth` (этапов в очереди по статусам).
- Время до решения: у каждой заявки хранятся `submitted_at` и `decided_at`, переходы — в `application_events` с отметками времени. Дашборд банка показывает время до решения и до выдачи, воронку и долю автоматических решений.
- Журнал вызовов внешних систем `integration_calls`: длительность, попытки, ошибки по каждому источнику; на дашборде — ошибки и задержки за последний час.
- Нагрузочный прогон — `loadtest/locustfile.py` (Locust): предприниматели одновременно подают заявки и опрашивают их, как кабинет, до решения. Итоги — `python loadtest/summarize.py <префикс>`.

## Нагрузочный прогон

**Стенд.** Одна машина: 2 vCPU (Intel Xeon 2,1 ГГц), 8 ГБ ОЗУ, Linux; на ней же — PostgreSQL 16, API (один процесс uvicorn), воркеры, симулятор внешних систем, nginx и сам генератор нагрузки. Демо-пауза между этапами отключена (`PIPELINE_STAGE_DELAY_SECONDS=0`, как в бою); симулятор отвечает с задержкой 150–600 мс на каждый запрос, как настоящие внешние системы (три источника на заявку). Все пользователи начинают в одну секунду — это худший случай «все подали одновременно», а не равномерный поток. Нагрузка на более сильном сервере и с генератором на другой машине будет ниже.

**Сценарий.** Каждый пользователь — одна из пяти демо-компаний (по кругу): создаёт черновик, подписывает согласия кодом, отправляет заявку и опрашивает её раз в секунду до решения. Исходы — автоматическое одобрение, встречное предложение, ручное рассмотрение, запрос выписки, отказ: все автоматические этапы (проверка полноты, три внешних источника, скоринг, решение) проходят все заявки. Заявки не принимаются и не выдаются, поэтому долговая нагрузка демо-компаний не растёт и прогон повторяем.

```bash
docker compose up -d --scale worker=1          # и --scale worker=3 для второй серии
pip install locust
locust -f loadtest/locustfile.py --headless --host http://localhost:8080 -u 50 -r 50 --run-time 10m --csv loadtest/out/50x1 --only-summary
python loadtest/summarize.py loadtest/out/50x1
```

**Что это значит.**

- Пропускная способность одного воркера — около 0,75 заявки в секунду: заявка занимает воркер ~1,3 с, почти всё это — три последовательных запроса во внешние системы (150–600 мс каждый) и ожидание. Три воркера дают ~2,1 заявки в секунду — рост почти линейный (×2,8), потому что воркеры ждут внешние системы, а не процессор. Следующий резерв — опрашивать ЕГРЮЛ, ФНС и БКИ параллельно внутри одного этапа (сейчас по очереди).
- Цель «при всплеске p95 ≤ 60 с, первое решение ≤ 10 с» на этом стенде выполняется при 50 одновременных заявках с одним воркером и при 100 — с тремя. Один воркер на 100 одновременных заявок — p95 120 с: очередь из 95 этапов разбирается две минуты. Правило для эксплуатации: очередь `PENDING` больше 50 на воркер дольше пяти минут — добавить воркеры.
- API без ошибок во всех прогонах (0 из 11 тысяч запросов). Опрос статуса — 23–110 мс p50; в пик одновременной подачи 100 заявок (≈500 запросов записи за первые секунды на 2 vCPU, которые делят API, воркеры, БД и генератор нагрузки) p95 записи — 2,7–2,9 с, это выше цели «до 500 мс при обычной нагрузке», но укладывается в «до 3 с в пик». На выделенном сервере или с несколькими экземплярами API за балансировщиком пик сглаживается: API не хранит состояние.

**Что нашёл и исправил прогон** (до исправлений — те же сценарии на том же стенде):

- Очередь разбиралась «хором»: воркер брал этапы в порядке их появления, поэтому все 50 заявок сначала проходили проверку полноты, потом все — сбор сведений, и первое решение появлялось через 63 с — вместе с последним (p50 = 66 с). Теперь воркер ведёт заявки в порядке отправки: первое решение — через 3–4 с, p50 при 50 заявках и одном воркере — вдвое меньше при той же пропускной способности.
- 100 одновременных подач складывали API: пул соединений с БД (10 + 10) был меньше числа потоков (40), запросы ждали соединение 30 с и падали в 500, веб-шлюз отвечал 504; за шесть минут до решения дошли 5 заявок из 100. Теперь пул — по числу потоков, ожидание соединения — не дольше 10 с, после чего клиент получает 503 с `Retry-After` и текстом «Сервис перегружен. Попробуйте ещё раз через несколько секунд», а кабинет предлагает повторить. В прогоне после исправления — 100 из 100 заявок без единой ошибки.

## Ограничения измерения

Один прогон на одной машине с генератором нагрузки рядом — это оценка порядка величин и проверка, что система деградирует предсказуемо, а не падает; это не замер для договора об уровне обслуживания. Перед промышленной эксплуатацией нужны прогоны на целевой конфигурации с реальными задержками внешних систем и профилем поступления заявок по часам.
