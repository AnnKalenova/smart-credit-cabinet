# Модель кредитного процесса

Документ описывает, какой кредитный процесс реализует прототип: его границы, этапы, участников, данные и возможные исходы. Здесь же объяснено, что вошло в MVP и почему.

## Границы процесса

**Начало:** у действующего клиента банка (ИП или юрлица) возникла потребность в финансировании.
**Конец:** кредит выдан на расчётный счёт или заявка закрыта: отказ банка, отказ клиента, отзыв, истечение срока предложения.

Сопровождение после выдачи (мониторинг, пролонгация, реструктуризация) в MVP не входит. В кабинете есть только график платежей по выданному кредиту.

Предприниматель уже обслуживается в банке. Поэтому регистрации нет, а реквизиты, руководитель, обороты по счёту банк знает сам. Это главный источник упрощения для клиента.

## Участники и роли

| Роль | Кто | Что делает в процессе |
|---|---|---|
| Представитель бизнеса с правом подписи | собственник, генеральный директор, ИП, сотрудник по доверенности | подбирает продукт, подаёт заявку, подписывает согласия и договор, отвечает на запросы |
| Представитель без права подписи | бухгалтер, финансовый директор | готовит заявку и документы, видит ход рассмотрения и предложение, передаёт заявку на подпись руководителю |
| Конвейер (система) | воркеры кредитного конвейера | проверяет данные, собирает сведения, считает скоринг, принимает автоматическое решение |
| Кредитный аналитик (андеррайтер) | сотрудник банка | рассматривает нестандартные заявки, одобряет, запрашивает информацию, отказывает |
| Риск-менеджер | сотрудник банка | управляет параметрами политики (ключевая ставка), контролирует конвейер |

Разделение прав «готовит / подписывает» — ответ на целевую аудиторию из кейса: заявку часто оформляет не собственник, а бухгалтер.

## Этапы

```
Потребность → Подбор продукта → Черновик → Согласия → Отправка
  → Проверка полноты (PRECHECK)
  → Сбор данных (ENRICHMENT): ЕГРЮЛ/ЕГРИП, ФНС «Прозрачный бизнес», БКИ, обороты по счёту
  → Скоринг (SCORING): балльная модель, рейтинг A–E
  → Решение (DECISION): кредитная политика
      ├─ автоматическое одобрение / встречное предложение → Предложение
      ├─ запрос информации → клиент отвечает → снова проверка
      ├─ ручное рассмотрение → аналитик решает
      └─ отказ
  → Предложение → Выбор варианта → Подписание кодом → Выдача (АБС) → Кредит выдан
```

| Этап | Кто | Что происходит | Данные на входе | Результат |
|---|---|---|---|---|
| Подбор продукта | клиент | цель, сумма, срок → подходящие продукты с ориентировочной ставкой и платежом | обороты по счёту, ключевая ставка | выбранный продукт |
| Черновик | клиент | параметры кредита; данные компании подставлены автоматически; документы по правилам продукта | профиль клиента, правила продукта | черновик (автосохранение) |
| Согласия | подписант | согласие на запрос в БКИ и обработку данных, подпись кодом внутри кабинета | — | согласия с отметкой времени |
| Проверка полноты | система | диапазоны суммы и срока, цель, контрольные цифры ИНН, выручка, контакт, описание залога (если он обязателен или предложен), документы, согласия | заявка | → сбор данных или запрос уточнений |
| Сбор данных | система | запросы во внешние источники с повторами и журналом вызовов | ИНН, согласие | выписка ЕГРЮЛ, сведения ФНС, отчёт БКИ, обороты |
| Скоринг | система | 12 факторов, балл и рейтинг A–E, условная вероятность дефолта | все собранные данные | балл, рейтинг, вклад каждого фактора |
| Решение | система | стоп-факторы → противоречия → лимит и ставка → варианты → триггеры ручного рассмотрения | скоринг, продукт, ключевая ставка | одобрение, встречное предложение, запрос, ручное рассмотрение, отказ |
| Ручное рассмотрение | аналитик | досье, рекомендация системы, решение с комментарием | всё выше + переписка | предложение, запрос или отказ |
| Предложение | подписант | 1–2 варианта условий, объяснение решения, график; действует 10 дней | решение | выбранный вариант |
| Подписание | подписант | договор, график, заявление на выдачу — подпись кодом | предложение | подписанный договор |
| Выдача | система | открытие ссудного счёта и зачисление через АБС (симулятор), идемпотентно | договор | кредит, график платежей |

## Возможные исходы

- **Одобрение на запрошенных условиях** — автоматически или аналитиком.
- **Встречное предложение.** Банк готов дать деньги на других условиях: та же сумма на больший срок, меньшая сумма на тот же срок или другой продукт под ту же цель. Клиент выбирает вариант.
- **Запрос информации.** Заявка остаётся той же, данные сохраняются. После ответа клиента она снова проходит проверку. Запросить информацию может система (например, при противоречии в данных) или аналитик.
- **Отказ** — по стоп-факторам или решению аналитика, с понятной клиенту причиной. Можно подать новую заявку, данные скопируются.
- **Отказ клиента, отзыв заявки, истечение срока предложения** — заявка закрывается, история сохраняется.

## Где решает система, а где человек

Автоматика решает, когда риск понятен и сумма в пределах лимита автоматического решения. Человек подключается, когда:

- сумма выше лимита автоматического решения продукта (экспресс — 5 млн, оборотный — 10 млн, инвестиционный — 15 млн ₽);
- рейтинг D (повышенный риск);
- есть признаки, требующие экспертизы: налоговый долг свыше 300 тыс. ₽, смена руководителя за последние 6 месяцев, массовый адрес, недостоверность сведений, блокировки счетов, просрочка 31–90 дней;
- внешний источник данных не ответил после всех повторов;
- противоречие в данных не устранено за два раунда уточнений.

Даже на ручном рассмотрении система передаёт аналитику рекомендацию: какие условия она предложила бы и почему. Аналитик принимает решение быстрее и в рамках той же политики.

## Что вошло в MVP и почему (MoSCoW)

| Приоритет | Функция | Почему |
|---|---|---|
| Must | сквозной путь от потребности до выдачи | главное требование кейса |
| Must | банковская обработка: этапы, скоринг, решение, ручное рассмотрение | вторая половина конвейера |
| Must | прозрачный статус и «что дальше» на каждом шаге | клиент без банковской экспертизы должен понимать, что происходит |
| Must | сохранение данных и единая заявка при уточнениях | критерий «согласованность модулей» |
| Must | синтетические данные, моки внешних систем, Docker | автономность и проверяемость |
| Should | подбор продукта под задачу | клиент не знает, какой продукт ему нужен |
| Should | предзаполнение из данных банка, предварительный лимит | меньше ручного ввода |
| Should | встречные предложения с выбором варианта | итог не бинарный (стр. 15 кейса) |
| Should | права подписи: бухгалтер готовит, руководитель подписывает | реальная структура МСБ |
| Should | мониторинг конвейера и моделирование сбоев | enterprise-проработка, отказоустойчивость |
| Could | ИИ-помощник, распознавание документов | ИИ не обязателен; ценность ниже, чем у основного сценария |
| Won't (в прототипе) | реальные интеграции (СМЭВ, БКИ, УКЭП, АБС), залоги с оценкой, сопровождение после выдачи | вне рамок хакатона, заменены симуляторами |
