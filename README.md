# Умный кредитный кабинет предпринимателя

Цифровой кредитный конвейер для малого и микробизнеса. Хакатон «Альфа-Будущее», трек «Умный кредитный кабинет предпринимателя».

Предприниматель проходит весь путь в одном веб-кабинете: потребность → подбор продукта → заявка → проверка → предложение → подпись → деньги на счёте. Банк обрабатывает ту же заявку в едином конвейере: проверяет данные, собирает сведения из ЕГРЮЛ, ФНС и БКИ, считает скоринг и принимает решение. Решение автоматическое, когда риск понятен, и принимается кредитным специалистом, когда нужна экспертиза.

![Заявка в кабинете предпринимателя](docs/screenshots/11-counter-offer.png)

Интерфейс оформлен в духе цифровых продуктов Альфа-Банка; логотип и товарные знаки банка не используются ([THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md)).

## Чем выделяется: конструктор условий

Обычно встречное предложение или отказ — конец разговора: клиент не знает, при каких условиях банк скажет «да». Здесь, когда банк оценил заявку, предприниматель сам меняет сумму, срок, продукт, залог и поручительство и сразу видит решение банка: «Одобрим автоматически», «Предложим другие условия» или «Решение примет кредитный специалист», ставку, платёж и долю платежей в поступлениях на счёт.

- **Тот же расчёт, что у банка.** Работают та же балльная модель и та же кредитная политика, на сведениях ЕГРЮЛ, ФНС и БКИ, уже полученных по заявке. В базу ничего не пишется.
- **Подсказки «Что улучшит условия».** Каждая посчитана политикой: «Срок 24 мес. — одобрим автоматически вместо «предложим другие условия»», «Поручительство собственника — ставка 21% вместо 21,5%». Варианты, которые уже есть в предложении банка, не повторяются; если длинный срок снижает платёж, но увеличивает переплату, подсказка говорит об этом прямо.
- **Вариант банка узнаётся.** Если выбранные условия совпадают с вариантом из предложения, конструктор так и пишет и даёт «Выбрать этот вариант» — новая заявка не нужна.
- **Новая заявка в один клик.** «Подать заявку на этих условиях» закрывает текущее предложение и создаёт черновик с теми же данными и документами одной операцией; под кнопкой — честно, что останется сделать. Бухгалтер без права подписи передаёт условия руководителю, и у того они открываются в конструкторе.

## Быстрый старт

Нужны Docker Desktop (Windows, macOS) или Docker Engine 24+ с Compose v2 (Linux), свободные порты 8080, 8000, 8001.

```bash
git clone <ссылка на репозиторий>
cd smart-credit-cabinet
docker compose up -d --build
```

Первая сборка занимает 3–5 минут: скачиваются базовые образы и зависимости. Когда `docker compose ps` покажет сервисы в состоянии `healthy`, откройте:

| Что | Адрес |
|---|---|
| Веб-интерфейс | http://localhost:8080 |
| Swagger (API) | http://localhost:8080/api/docs |
| Swagger симулятора внешних систем | http://localhost:8001/docs |
| Метрики Prometheus (только с этого компьютера) | http://localhost:8000/metrics |

При первом запуске API сам применяет миграции и загружает синтетические данные. Отдельных шагов не нужно.

```bash
docker compose logs -f api worker        # логи конвейера
docker compose up -d --scale worker=3    # несколько воркеров
docker compose down                      # остановить
docker compose down -v                   # остановить и удалить данные (следующий запуск — с чистой базы)
```

Запуск без Docker — см. [Разработка без Docker](#разработка-без-docker).

## Пошаговый сценарий проверки

Основной путь, 3–4 минуты:

1. Войти как `smirnov`. На главной — предварительный лимит, обороты по счёту, данные компании.
2. «Подобрать кредит» → «Закупка товара, сырья, материалов», 3 000 000 ₽, 12 мес. → «Оформить» у «Оборотного кредита».
3. В черновике данные компании и выручка уже заполнены. «Подписать согласия» → «Вставить код» → «Подписать» → «Отправить заявку».
4. Конвейер показывает в реальном времени: проверка данных → ЕГРЮЛ → ФНС → БКИ → рейтинг → условия. Через 10–15 секунд — предложение с объяснением.
5. «Выбрать этот вариант» → «Подписать кодом» → кредит выдан, график платежей доступен.
6. Войти как `analyst` → «Мониторинг»: заявка в воронке, время до решения, вызовы внешних систем.

Конструктор условий, 2–3 минуты:

1. Войти как `kuznetsova` → «Подобрать кредит» → «Открыть точку или сделать ремонт», 1 000 000 ₽, 12 мес. → «Оформить» у «Экспресс-кредита» → подписать согласия и отправить.
2. Через 10–15 секунд — встречное предложение: вся сумма на 18 мес. или 710 000 ₽ на 12 мес.
3. Ниже, в «Конструкторе условий», — «Предложим другие условия». Если выбрать срок 18 мес., конструктор узнает вариант банка и предложит «Выбрать этот вариант». У подсказки «Срок 24 мес.» нажать «Применить»: вердикт меняется на «Одобрим автоматически», платёж — 51 632 ₽.
4. «Подать заявку на этих условиях» → подтвердить. Текущее предложение закроется, откроется новая заявка с теми же данными: подписать согласия, отправить — одобрено автоматически.

Остальные ветки (ручное рассмотрение, запрос уточнений, отказ, права подписи, отказоустойчивость, сбой выдачи, ключевая ставка) описаны пошагово с ожидаемыми результатами в **[docs/test-scenarios.md](docs/test-scenarios.md)**.

Всё то же самое проверяется автоматически на поднятом стенде:

```bash
pip install httpx
python e2e/api_scenarios.py --base-url http://localhost:8080        # 8 сквозных сценариев
npx newman run docs/postman/smart-credit-cabinet.postman_collection.json   # 88 запросов, 127 проверок
```

## Что реализовано

**Кабинет предпринимателя**
- подбор продукта под задачу: цель, сумма, срок → подходящие продукты с диапазоном ставки, платежом и списком документов;
- предварительный лимит на главной по оборотам на счёте;
- черновик с автосохранением: реквизиты, руководитель, оценка выручки подставляются из данных банка; документы запрашиваются только по правилам продукта; в «Обеспечении» — поручительство собственника у любого продукта и залог там, где продукт его допускает, а предварительный расчёт сразу учитывает эти скидки;
- простая электронная подпись кодом внутри кабинета — без SMS и почты;
- «конвейер» заявки: пять шагов, «сейчас / что дальше», живой подшаг обработки, история событий;
- ответ на запрос банка в той же заявке, переписка со специалистом, уведомления в кабинете;
- предложение с объяснением: что помогло решению, что снизило оценку, из чего складывается ставка; встречные варианты на выбор;
- **конструктор условий**: решение банка при других сумме, сроке, продукте, залоге и поручительстве, подсказки «что улучшит условия», выбор варианта банка без новой заявки, новая заявка на выбранных условиях в один клик; сотрудник без права подписи передаёт условия руководителю;
- проект договора и график платежей, подпись, выдача, раздел «Кредиты»;
- разделение прав: бухгалтер готовит заявку, а подписывает, выбирает условия и отказывается от предложения руководитель;
- отзыв заявки; повторная подача — параметры, залог и документы переносятся в новый черновик (ссылкой на тот же файл, без копирования), согласия подписываются заново. По закрытой заявке — одна незакрытая новая;
- вёрстка работает и на телефоне.

**Обработка в банке**
- конвейер этапов: проверка полноты → сбор данных → скоринг → решение → выдача; воркеры масштабируются;
- балльная модель (12 факторов, рейтинг A–E) и кредитная политика: стоп-факторы, лимит по оборотам и платёжеспособности, ставка от ключевой ставки Банка России, встречные варианты, триггеры ручного рассмотрения;
- рабочее место аналитика: очередь с SLA и отметкой «клиент ждёт ответа», досье (скоринг с вкладом факторов, ответы ЕГРЮЛ/ФНС/БКИ, обороты, расчёт лимита и ставки, журнал), решение — одобрить с корректировкой условий, запросить информацию, отказать; повтор выдачи, если АБС была недоступна;
- мониторинг: воронка, доля автоматических решений, время до решения и выдачи, ошибки внешних систем; моделирование сбоев;
- параметры политики: ключевая ставка меняется риск-менеджером без релиза.

**Enterprise-аспекты:** JWT и роли с проверкой доступа на уровне записи; защита от подбора пароля по логину, адресу и паре «логин + адрес» плюс ограничение частоты входа в nginx; лимиты на коды подписи; Content-Security-Policy на страницах интерфейса; проверка `X-Request-ID`; проверка формата файлов по содержимому и безопасные имена файлов; ограничения на все поля ввода, ошибки — понятным списком на русском, символ NUL и прочий некорректный ввод — 422, а не 500; параметры SQL не попадают в логи; демо-функции выключаются вместе с `DEMO_MODE`; журнал аудита; оптимистичная блокировка и advisory-блокировки против двойных нажатий; идемпотентная выдача, а при долгом сбое АБС — повтор специалистом; повторы с экспоненциальной паузой; воркер переживает изменения заявки во время этапа, а этап с упавшего воркера возвращается в очередь; healthcheck у каждого контейнера; JSON-логи с `request_id`; метрики Prometheus; миграции; lock-файлы с хешами; CI. Подробно — [docs/architecture.md](docs/architecture.md).

## Требования к окружению

| | Docker-запуск | Разработка без Docker |
|---|---|---|
| ОС | Windows 10/11 (Docker Desktop, WSL 2), macOS, Linux | любая |
| Инструменты | Docker 24+, Docker Compose v2 | Python 3.13, Node.js 22, PostgreSQL 16 |
| Память | около 1 ГБ RAM на контейнеры (плюс сам Docker Desktop: 2–4 ГБ) | — |
| GPU | не нужен | не нужен |
| Сеть | только при первой сборке (образы и пакеты) | для установки зависимостей |

Версии зафиксированы: Python — `backend/requirements.txt` и `integrations-mock/requirements.txt` (с хешами, `pip --require-hashes`, для Linux, macOS и Windows), Node — `frontend/package-lock.json`, базовые образы — теги версий в Dockerfile и `docker-compose.yml` (`python:3.13-slim`, `postgres:16-alpine`, `nginx:1.27-alpine`, `node:22-alpine`). Теги фиксируют версию, но получают патчи безопасности; для побитовой воспроизводимости в рабочей среде образы закрепляются по digest (`image@sha256:…`) во внутреннем реестре.

## Конфигурация

Все параметры задаются переменными окружения. Без файла `.env` работают значения по умолчанию. Полный список с комментариями — [.env.example](.env.example).

```bash
cp .env.example .env   # при необходимости
```

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `WEB_PORT` / `API_PORT` / `MOCK_PORT` | 8080 / 8000 / 8001 | порты на хосте |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | credit / credit / credit | база данных |
| `JWT_SECRET` | демо-значение | секрет подписи токенов — смените вне демо-стенда; при `DEMO_MODE=false` API с демо-значением не стартует |
| `DEMO_MODE` | true | демо-режим: демо-учётки на странице входа, код подписи в окне подписи, кнопка «Пример файла», моделирование сбоев. При `false` всё это выключено (API отвечает 404), демо-пользователи не создаются, а созданные раньше отключаются; код подписи должен доставлять канал банка — в этой сборке он не подключён |
| `SEED_ON_START` | true | загружать синтетические данные при первом запуске |
| `DEFAULT_KEY_RATE` | 14.0 | ключевая ставка при первом запуске; дальше меняется в интерфейсе |
| `PIPELINE_STAGE_DELAY_SECONDS` | 1.2 | пауза между этапами, чтобы в демо было видно движение; в рабочей среде 0 |
| `INTEGRATION_TIMEOUT_SECONDS` / `INTEGRATION_MAX_ATTEMPTS` / `INTEGRATION_BACKOFF_BASE_SECONDS` | 5 / 5 / 2 | таймаут, число попыток и база паузы при вызове внешних систем (выдача через АБС — до 30 попыток) |
| `OFFER_VALID_DAYS` / `MANUAL_REVIEW_SLA_HOURS` | 10 / 4 | срок действия предложения и SLA ручного рассмотрения |

### Разработка без Docker

```bash

cd backend
pip install --require-hashes -r requirements.txt -r requirements-dev.txt
export DATABASE_URL=postgresql+psycopg://credit:credit@localhost:5432/credit UPLOAD_DIR=./uploads
alembic upgrade head && python -m app.seed
uvicorn app.main:app --port 8000          # API
python -m app.worker.runner               # воркер (в другом терминале)

cd ../integrations-mock && pip install --require-hashes -r requirements.txt
uvicorn app.main:app --port 8001          # симулятор

cd ../frontend && npm ci && npm run dev   # http://localhost:5173, /api проксируется на :8000
```

В Windows команды те же, но переменные окружения задаются в PowerShell: `$env:DATABASE_URL="postgresql+psycopg://credit:credit@localhost:5432/credit"`. Проще всего разрабатывать в WSL 2 или запускать стенд в Docker.

### Развёртывание на сервере

Тот же `docker compose up -d --build` на VPS с Docker. Задайте в `.env` свой `JWT_SECRET`, пароль БД и `WEB_PORT=80`. HTTPS — через внешний обратный прокси или балансировщик.

## Тесты

```bash
cd backend && pytest                       # 206 тестов: 113 модульных + 93 интеграционных
ruff check . && ruff format --check .      # линтер и форматирование
cd ../frontend && npm run build            # проверка типов TypeScript и сборка
python e2e/api_scenarios.py --base-url http://localhost:8080   # сквозные сценарии на стенде
python e2e/ui_tour.py --base-url http://localhost:8080         # UI-прогон в браузере (Playwright) со скриншотами
```

Интеграционным тестам нужен PostgreSQL с отдельной базой `credit_test`: по умолчанию `postgresql+psycopg://credit:credit@127.0.0.1:5432/credit_test`, другой адрес задаётся переменной `TEST_DATABASE_URL`. Тесты пересоздают схему этой базы, поэтому её имя обязано оканчиваться на `_test`. Модульные тесты базу не используют и запускаются без PostgreSQL: `pytest tests/test_finance.py tests/test_scoring.py tests/test_policy.py tests/test_statuses_checks.py tests/test_storage_worker.py`.

Сквозные сценарии и Postman-коллекция рассчитаны на чистый стенд: выданные кредиты увеличивают долговую нагрузку демо-компаний. Перед повторным прогоном — `docker compose down -v && docker compose up -d --build`.

CI ([.github/workflows/ci.yml](.github/workflows/ci.yml)) на каждый push: линтер и тесты с PostgreSQL → сверка OpenAPI в `docs/` с кодом → сборка интерфейса → `docker compose up --build --wait` → сквозные сценарии и Postman-коллекция через nginx.
